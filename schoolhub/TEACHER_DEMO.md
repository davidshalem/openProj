# SchoolHub – דף הצצה למורה

מטרת השיעור: להראות לתלמידים שתכנות הוא חלק מבניית מערכת, אבל אינו כל התהליך.

המסר המרכזי:

**משתמש → בקשה → Flask → לוגיקה/נתונים → Jinja → HTML → משתמש**

ובמבט רחב:

**צורך → דרישות → תכנון → מימוש → בדיקות → מערכת**

## הכנה לפני השיעור

מתוך תיקיית `schoolhub`:

```bash
python -m pip install -r requirements.txt
python app.py
```

פתחו מראש:

- בדפדפן: <http://127.0.0.1:5000>
- בעורך: `app.py`, `data.py`, `templates/dashboard.html`, `templates/students.html`, `templates/grades.html`

ודאו שה-Terminal גלוי. `debug=True` גורם ל-Flask להיטען מחדש לאחר שמירת קובץ. זכרו: שינויי נתונים דרך הטפסים נשמרים בזיכרון בלבד; טעינה מחדש של השרת מחזירה את נתוני המקור מ-`data.py`.

## תכנית שיעור מומלצת – כ-20 דקות

### שלב 1 – הצגת המוצר בלי קוד (דקות 0–3)

פתחו את לוח הבקרה בכתובת <http://127.0.0.1:5000>. עברו בקצרה בין לוח הבקרה, התלמידים והציונים. אל תפתחו עדיין את הקוד.

שאלו:

- "מי המשתמשים של המערכת?"
- "מה הצורך שהמערכת מנסה לפתור?"
- "אילו פעולות תלמיד צריך לבצע?"
- "אילו פעולות מורה צריך לבצע?"
- "מהן הדרישות שאתם כבר מזהים במסכים?"
- "מה לדעתכם קורה כשאני לוחץ על תלמידים?"

סכמו את הדרישות שמומשו: צפייה בתמונת מצב, הצגת תלמידים, חיפוש, הוספת תלמיד, צפייה בציונים ועדכון ציון.

### שלב 2 – צד לקוח וצד שרת (דקות 3–6)

פתחו את `app.py` והציגו את route ה-Dashboard:

```python
@app.route("/")
def dashboard():
    return render_template(
        "dashboard.html",
        students_count=len(students),
        teachers_count=len(teachers),
    )
```

הסבירו:

1. הדפדפן מבקש את `/`.
2. Flask מוצא פונקציה שמתאימה לנתיב.
3. Python מחשב נתונים.
4. `render_template` מעביר אותם ל-Jinja.
5. Jinja בונה HTML.
6. הדפדפן מציג את ה-HTML.

שאלו:

- "מי אחראי לקבל את הבקשה?"
- "האם הדפדפן מריץ כאן את קוד ה-Python?"
- "איפה לדעתכם מחושב מספר התלמידים?"

### שלב 3 – משתנים וירושה ב-Jinja (דקות 6–8)

פתחו את `templates/dashboard.html` והצביעו על:

```jinja2
{% extends "base.html" %}
{% block content %}
{{ students_count }}
```

לאחר מכן פתחו לרגע את `templates/base.html`. הסבירו שה-header, הניווט וה-footer כתובים פעם אחת, וכל עמוד מספק רק את ה-`content` שלו.

שאלו:

- "מאיפה הגיע `students_count`?"
- "למה כדאי לא לשכפל את הניווט בכל קובץ?"
- "מה יקרה לכל המסכים אם נשנה את `base.html`?"

### שלב 4 – Jinja loop והוספת נתונים (דקות 8–11)

פתחו את `templates/students.html` ליד `DEMO 3` והציגו:

```jinja2
{% for student in students %}
    {{ student.name }}
{% endfor %}
```

הסבירו: Flask שולח רשימה; Jinja מייצרת שורת HTML אחת לכל איבר. לא כתבנו חמש שורות נפרדות, ואותו קוד יעבוד גם עם מאה תלמידים.

כעת פתחו את `data.py` ליד `DEMO 2` והוסיפו בסוף הרשימה:

```python
{"id": 6, "name": "רוני ישראלי", "class_name": "י״ב3", "average": 95.0},
```

שמרו ורעננו את `/students`.

שאלו:

- "כתבנו HTML חדש עבור רוני?"
- "מאיפה הגיע המשתנה `students` לתבנית?"
- "למה לא כתבנו שורת HTML לכל תלמיד?"
- "מה יקרה אם יהיו 10,000 תלמידים?"
- "איפה מערכת אמיתית תשמור את הנתונים?"

### שלב 5 – שינוי דרישה ותנאי עסקי (דקות 11–13)

ב-`templates/dashboard.html`, ליד `DEMO 1`, שנו:

```html
<h1>ברוכים הבאים ל-SchoolHub</h1>
```

ל:

```html
<h1>ברוכים הבאים לשיעור הנדסת תוכנה</h1>
```

שמרו ורעננו. אמרו: "שינוי קטן בדרישה גורם לשינוי במערכת."

לאחר מכן ב-`templates/students.html`, ליד `DEMO 4`, הראו:

```jinja2
{% if student.average >= 90 %}
    מצוין
{% else %}
    רגיל
{% endif %}
```

שנו את 90 ל-95 ורעננו. זהו שינוי בדרישה עסקית, לא שינוי עיצוב.

שאלו:

- "אילו תלמידים שינו סטטוס?"
- "מי החליט מה פירוש 'מצוין' — המתכנת או בעל הדרישה?"

### שלב 6 – Form, GET, POST ו-Validation (דקות 13–17)

עברו אל `/grades`. בחרו תלמיד באמצעות הרשימה. הסבירו שבחירה והצגה הן בקשת GET: בקשה לקבל מידע.

פתחו את `app.py` ליד `DEMO 6`:

```python
@app.route("/grades", methods=["GET", "POST"])
```

פתחו גם את `templates/grades.html` והראו:

```html
<form method="POST">
```

שנו ציון חוקי, למשל 92 ל-95, ולחצו "עדכן ציון". עקבו עם האצבע:

**Browser ↓ POST Request ↓ Flask ↓ Python ↓ עדכון הנתונים ↓ render_template ↓ HTML חדש**

שאלו:

- "עד עכשיו השרת שלח מידע לדפדפן. מה חדש עכשיו?"
- "איפה נמצא הערך שהמשתמש הקליד?"
- "מה יקרה אם אכניס 150?"
- "מי צריך לבדוק שהציון חוקי — הדפדפן, השרת, או שניהם?"

כדי להדגים 150 למרות מגבלת שדה ה-HTML, אפשר לפתוח את כלי המפתחים בדפדפן ולהסיר זמנית את `max="100"`, או להריץ ב-Terminal:

```bash
curl -X POST -d "student_id=1&subject=מתמטיקה&grade=150" http://127.0.0.1:5000/grades
```

השרת יציג: **"הציון חייב להיות בין 0 ל-100"** ולא ישמור את הערך. הדגישו: בדיקת HTML משפרת חוויית משתמש; בדיקת Python מגינה על המערכת גם אם עוקפים את הדפדפן.

### שלב 7 – באג לוגי בטוח (דקות 17–19)

הפרויקט תקין כברירת מחדל. כדי ליצור באג ידנית, פתחו את `templates/students.html` ליד `DEMO 4` ושנו:

```jinja2
{% if student.average >= 90 %}
```

ל:

```jinja2
{% if student.average <= 90 %}
```

שמרו ורעננו את `/students`. תלמידים בעלי ממוצע נמוך יסומנו "מצוין". אין קריסה ואין הודעת שגיאה, אבל התוצאה אינה עומדת בדרישה.

שאלו:

- "המערכת רצה. אז למה היא עדיין לא תקינה?"
- "מה ההבדל בין Syntax Error ל-Logic Error?"
- "איזו בדיקה הייתה מגלה את הבאג?"

בסיום החזירו את התנאי ל-`>= 90`.

### שלב 8 – סיכום (דקות 19–20)

חזרו אל לוח הבקרה וסכמו:

```text
צורך
  ↓
דרישות
  ↓
תכנון
  ↓
מימוש
  ↓
בדיקות
  ↓
מערכת
```

סיימו במשפט:

**"לדעת לתכנת זה לא אותו דבר כמו לדעת לבנות מערכת."**

## אם נשארו עוד שתי דקות

פתחו את `tests/test_app.py`. הראו שבדיקה היא קוד שמפעיל את המערכת ושואל אם ההתנהגות שקיבלנו תואמת לדרישה. הריצו:

```bash
python -m unittest discover -s tests -v
```

הצביעו במיוחד על הבדיקות שחוסמות 150 ומינוס 1. שאלו: "אם נשנה את דרישת הציון ל-0–120, אילו חלקים נצטרך לעדכן?"

## נקודות תכנון שכדאי לומר בקול

- `data.py` הוא מקור הנתונים הזמני; מסד נתונים הוא המשך טבעי, לא תנאי להבנת הזרימה.
- `base.html` מונע שכפול ומדגים מבנה משותף.
- GET מתאים לקבלת תצוגה; POST מתאים לשליחת שינוי.
- אין לסמוך על קלט משתמש. ולידציה בצד שרת נשארת חובה גם אם יש בדיקה ב-HTML.
- מערכת יכולה לרוץ ללא שגיאת תחביר ועדיין לתת תשובה שגויה.
- כל שינוי דרישה עשוי להשפיע על נתונים, לוגיקה, תצוגה ובדיקות.
